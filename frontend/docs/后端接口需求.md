## 一、时间线：四个可选字段（上一轮已提，仍需要）

时间线支持**拖动移动**和**拖缘调整大小**，位置与尺寸都存在 `Timeline` 上。

```json
{
  "id": "tl_abc123",
  "name": "案件时间线",
  "direction": "horizontal",
  "points": [ ... ],
  "x": 88,          // 面板在画布上的左上角 X
  "y": 44,          // 面板左上角 Y
  "width": 760,     // 横向面板宽度（direction=horizontal 时有效，缺省 760）
  "height": 400     // 纵向面板高度（direction=vertical 时有效，缺省 400）
}
```

要求：

1. `x` / `y` / `width` / `height` 四个字段**存取往返**，允许缺省。
2. 用 JPA 映射 JSON 时注意 `Integer`/`Double` 的 null，别把缺省值强转成 0。

## 二、同一对对象之间的多条关系**必须都保留**（本轮强依赖）

**现象**：画布里 A→B 已经有一条关系，再建一条 B→A（或同向另一条），保存后只剩一条——像是按 `(source, target)` 去重了。

**本轮变化**：前端现在会把同一对对象之间的多条关系**平行并排**画出来（A↔B 之间「师徒」和「怀疑」各占一条，不再重叠成一条）。

**要求**：

- `relationships` 数组**原样整体保存**，以 `id` 为准；
- **不要**按 `source+target`（或 `source+target+type`）去重 / 覆盖；
- 同一对对象之间多条不同 `type`（单向 / 双向 / 虚线）的关系是合法数据。

> 只要后端一去重，用户就永远只能看到一条线，前端的平行排布也就失去意义。

## 三、关系图提取 `extract`：请后端自查（本轮重点）

**现象**：在「人物关系图」里点「新增关系图」，提示「已提取」，但点开图里**空空如也**。也就是说 `POST /books/{bookId}/relation-graphs/extract` 返回了成功，`data` 却是空的。

**前端已加的兜底**（后端修好后会自动优先用后端结果）：

1. 调 `extract`；
2. 判定「可用」的条件是：`data.nodes.length > 0` **且**（`data.edges.length > 0` 或当前画布本来就没有关系）；
3. 不满足 → 退回**当前页画布**推导：`canvas.objects → nodes`、`canvas.relationships → edges`；
4. 详情层新增了「从画布重新提取」按钮，走同一套判定，并且会提示数据来自「全书」还是「当前画布」。

**请后端按下面几条确认 / 修正实现**：

1. `extract` 应遍历该书**所有 page 的画布**，把每个 `CanvasObject` 映射成 `GraphNode`、每个 `Relationship` 映射成 `GraphEdge`。
2. `GraphNode.id` 必须**等于画布对象的 `id`**（`GraphEdge.source/target` 引用同一套 id）。不要自己另起 `obj_1` 这类编号，否则前端无法与画布关联，也无法做「人物↔人物」过滤。
3. `objectTypes` 按 `CanvasObject.type` 过滤（`person` / `thing` / `event`），`relationTypes` 按 `Relationship.type` 过滤（`unidirectional` / `bidirectional` / `dashed`）。
4. 确实没有可提取的数据时，请返回 `{"nodes": [], "edges": []}`，不要报 500，也不要返回 `data: null`。
5. **最要紧的一条**：只要画布里有关系，`edges` 就不能为空。

**自查命令**：

```bash
BASE=http://localhost:8080/api

# 1. 先看某个 page 的画布到底有没有对象和关系
curl -s "$BASE/pages/1/canvas" | head -c 800

# 2. 再直接调 extract，对比数量是否与上面一致
curl -s -X POST "$BASE/books/1/relation-graphs/extract" \
  -H 'Content-Type: application/json' \
  -d '{"objectTypes":["person","thing"],"relationTypes":["unidirectional","bidirectional","dashed"]}'
```

## 四、确认项（schema 已支持，请确保实现真的做到）

### 1. `CanvasObject.customFields` / `style` 无损往返

前端把人物资料（年龄 / 职业 / 时间 / 地点 / 类别 / 备注）存在 `customFields` 里：

```json
{
  "id": "obj_x1",
  "type": "person",
  "name": "张远山",
  "customFields": { "age": "35", "occupation": "法医", "description": "..." },
  "style": {}
}
```

要求：任意 key-value 的 `Record<string, unknown>` 原样存取，**不要**把 `{}` 丢失成 `null`（前端判空依赖 `{}` 可迭代），也**不要**过滤未知字段。

### 2. `Annotation.content` 存原始 HTML，不做清洗

注解是完整富文本（加粗 / 斜体 / 下划线 / 删除线 / 字号 / 字色 / 背景色），HTML 片段存在 `content`：

```json
{ "id": "ann_1", "content": "<h4 class=\"anno-h\">批注标题</h4><p>正文<span style=\"color:#9C5A50\">带颜色</span><b>加粗</b></p>" }
```

要求：DB 用 TEXT/CLOB；读写**不做白名单过滤、不转义、不剥 style 属性**。

### 3. `PUT /pages/{id}/canvas` 语义

- **覆盖式**：请求体里的四个数组就是该页全部数据（前端先 GET 再改再 PUT）。
- **空数组 = 清空**：`"objects": []` 必须把该页对象清空，不能跳过。
- 建议整包事务写入，失败则整包不动。

### 4. 成功码与文档不一致（建议改文档）

文档写成功码 `code: 0`，实际实现返回 `code: 200`。前端已两者兼容，但请把 OpenAPI 文档同步成实际值。

### 5. `CanvasResponse.background`

画布背景（`plain | grid | dot | line`）随画布保存。`GET /canvas` 缺省时前端回落 `plain`，只要保证传了能存、能回即可。

## 五、关系图接口（本身够用，无需新增字段）

前端流程：

1. `GET /api/books/{bookId}/relation-graphs` 列表 → 点开某张 → `GET /api/relation-graphs/{id}`。
2. **新增**：`POST /api/books/{bookId}/relation-graphs` 建壳 → `POST .../extract` 提取 → `PUT /api/relation-graphs/{id}/data` 保存初始数据。
3. **编辑**：对象（增 / 删）、关系（增 / 删）每次变更整体 `PUT /api/relation-graphs/{id}/data`。
4. `data.nodes` / `data.edges` 请保证是数组（前端已容错 `null`，但别主动给 `null`）。

### 5.1 详情返回的 `data` 形态（可选统一，非阻塞）

现状：`GET /api/relation-graphs/{id}` 返回的 `data` 是库里的 **JSON 字符串**，解析后的
`nodes` / `edges` 平铺在顶层（`RelationGraphDetailVO`），即：

```json
{ "id": 4, "name": "爱我国防",
  "data": "{\"nodes\":[...],\"edges\":[...]}",
  "nodes": [...], "edges": [...] }
```

而上面第 4 条和前端类型 `RelationGraphDetailResponse` 期望的是 `data` 为**对象**。
两者的差异曾导致「新建关系图正常、重新打开却显示空图」。

前端已在 `src/api/relationGraph.ts` 做归一（优先读顶层 `nodes`/`edges`，缺失再解析 `data` 字符串），
所以**不需要后端改动**。若想统一契约，建议后续二选一：

- 方案 A（推荐）：`data` 直接返回对象 `{"nodes":[],"edges":[]}`，与 `PUT .../data` 的入参保持一致；
- 方案 B：保留字符串 `data`，但正式在文档里写明「详情以顶层 `nodes` / `edges` 为准」，
  前端随后可以删掉字符串解析分支。

## 六、族谱图接口（本轮新增 · **需要后端实现**）

族谱图以前存在浏览器 localStorage 里（换设备就丢），现在改成与「关系图」**完全同构**的一套接口，
数据落到后端。请照 `relation-graphs` 那一套原样复制一份：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/books/{bookId}/family-trees` | 族谱图列表 |
| POST | `/api/books/{bookId}/family-trees` | 创建族谱图（body `{"name":"沈氏家族"}`） |
| GET | `/api/family-trees/{id}` | 族谱图详情 |
| PUT | `/api/family-trees/{id}` | 改元信息（body `{"name":"..."}`，可选） |
| DELETE | `/api/family-trees/{id}` | 删除族谱图 |
| PUT | `/api/family-trees/{id}/data` | 保存族谱数据（整体覆盖） |

载荷形状（`PUT .../data` 的入参、与详情返回的顶层内容一致）：

```json
{
  "members": [
    { "id": "fm_a1b2c", "name": "沈砚清", "gender": "male", "birth": "1901", "death": "1968" },
    { "id": "fm_d3e4f", "name": "程婉之", "gender": "female", "birth": "1904" }
  ],
  "relations": [
    { "id": "fr_x1", "type": "spouse", "from": "fm_a1b2c", "to": "fm_d3e4f" },
    { "id": "fr_x2", "type": "parent-child", "from": "fm_a1b2c", "to": "fm_z9" }
  ]
}
```

字段约定：

- `gender` 取值 `male | female | unknown`。
- `type` 取值 `parent-child`（`from` 是父/母、`to` 是子女）或 `spouse`（互为配偶）。
- `birth` / `death` 是**纯文本**年份（如 `"1901"` 或 `"1901-1968"`），不是日期类型，**别做日期解析**。
- `members[].id` / `relations[].id` 是**前端生成的字符串**，除 `name` 外都可缺省。
  请按 id 整体覆盖保存，**不要去重、不要过滤未知字段**。

### 6.1 详情返回形态

与关系图同一套约定（见 5.1）：`data` 可以是 JSON 字符串，
但请把解析后的 `members` / `relations` **平铺在详情响应的顶层**：

```json
{ "id": 1, "bookId": 1, "name": "沈氏家族",
  "data": "{\"members\":[...],\"relations\":[...]}",
  "members": [...], "relations": [...] }
```

前端已在 `src/api/familyTree.ts` 做归一（优先顶层，缺失再解析字符串），两种形态都能吃。
**新建一张族谱图时请初始化成空数组**（`members: []`、`relations: []`），不要给 `null`。

### 6.2 建表提示

一张 `family_tree` 主表即可：`id, book_id, name, data TEXT, created_at, updated_at`，
`data` 用 TEXT 存原始 JSON 字符串，与 `relation_graph` 完全一致。

    {"id":"fm_b","name":"程婉之","gender":"female","birth":"1904"},

  ]

curl -s "$BASE/family-trees/$FT"   # 顶层 members / relations 应各有 3 / 2 条
curl -s -X DELETE "$BASE/family-trees/$FT"

## 八、可以直接发给后端的 prompt（本轮 · 族谱图）

## 九、画布尺寸字段 `canvasWidth` / `canvasHeight`（本轮新增 · **需要后端实现**）

### 背景

前端画布从「无限扩展」改成了**一张有明确尺寸的纸**：用户在工具栏「画布尺寸」里设定宽高，
超出的部分用滚动条看。这张纸的尺寸必须**跟着画布一起存到后端**（换设备 / 换浏览器不丢），
前端只在后端尚未支持时才用 localStorage 兜底。

### 现状（为什么必须改）

`CanvasResponse` 顶层标了 `@JsonIgnoreProperties(ignoreUnknown = true)` 但**没有**这两个属性的
getter/setter，所以：

- `PUT /api/pages/{id}/canvas` 收到 `canvasWidth` / `canvasHeight` 时**静默丢弃**；
- `GET` 返回时也**永远不会带出**这两个字段。

（子对象级别的扩展字段有 `Extensible` 的 any-setter/getter 兜底，**顶层没有**，这就是问题所在。）

### 改法（约 10 行）

`dto/CanvasResponse.java` 顶层类加两个字段 + getter/setter，其余什么都不用动：

```java
/** 画布（纸张）宽度，画布坐标系的逻辑像素，可空（老数据缺省，前端有默认值兜底） */
private Double canvasWidth;
/** 画布（纸张）高度，可空 */
private Double canvasHeight;

public Double getCanvasWidth() { return canvasWidth; }
public void setCanvasWidth(Double canvasWidth) { this.canvasWidth = canvasWidth; }
public Double getCanvasHeight() { return canvasHeight; }
public void setCanvasHeight(Double canvasHeight) { this.canvasHeight = canvasHeight; }
```

注意：

1. **不要**在 `normalize()` 里给它们填默认值或做非空处理——可空即可，缺省表示「前端自己兜底」。
2. `savePageCanvas` 的 `writeValueAsString(normalized)` 会自动带上这两个字段，无需改。
3. 取值范围由前端把关（600–8000），后端不做校验，**原样存取**。

### 数据格式（前端实际发送 / 期望接收）

```json
// PUT /api/pages/{id}/canvas 的请求体（节选）
{
  "background": "dot",
  "canvasWidth": 800,
  "canvasHeight": 600,
  "objects": [],
  "relationships": [],
  "annotations": [],
  "timelines": []
}

// GET /api/pages/{id}/canvas 的返回体（节选）——要求原样带出
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "background": "dot",
    "canvasWidth": 800,
    "canvasHeight": 600,
    "objects": [],
    "relationships": [],
    "annotations": [],
    "timelines": []
  }
}
```

### 自测

```bash
BASE=http://localhost:8080/api
# 1. 写入带尺寸的画布
curl -s -X PUT "$BASE/pages/1/canvas" -H 'Content-Type: application/json' -d '{
  "background":"plain","canvasWidth":800,"canvasHeight":600,
  "objects":[],"relationships":[],"annotations":[],"timelines":[]}' | grep -o "canvasWidth[^,]*"
# 2. 读回：必须能看到 "canvasWidth":800,"canvasHeight":600（现在会被吞掉）
curl -s "$BASE/pages/1/canvas" | grep -o "canvasWidth[^,]*"
```

验收：PUT 的返回体和 GET 的返回体里都出现 `canvasWidth` / `canvasHeight`，数值与写入一致；
老画布（无这两个字段）读写不受影响。

### 可以直接发给后端的 prompt

> 请给「推演录」后端的画布模型补两个可空字段 `canvasWidth` / `canvasHeight`：
> 在 `dto/CanvasResponse.java` 顶层类里加 `private Double canvasWidth; private Double canvasHeight;`
> 及其 getter/setter 即可（约 10 行），不要动 `normalize()`、不要加校验、不要给默认值。
> 背景：前端画布改成固定尺寸纸张后，尺寸要随 `PUT /GET /api/pages/{id}/canvas` 原样往返；
> 现在顶层类 `@JsonIgnoreProperties(ignoreUnknown=true)` 会把这两个未知字段静默丢弃，
> 导致用户的画布尺寸无法跨设备保存（子对象有 `Extensible` any-setter 兜底，顶层没有）。
> 改完用文档第九节的两条 curl 自测：PUT 与 GET 的返回体里都要出现
> `"canvasWidth":800,"canvasHeight":600`，老画布（无字段）读写不受影响。

## 十、书架排序字段 `contentUpdatedAt`（本轮新增 · **需要后端实现**）

### 背景

书架「按最近编辑」排序之前按 `Book.updatedAt` 排，而 `PUT /api/books/{id}`（重命名、换封面）
也会刷新 `updatedAt`，导致**改个书名就把书顶到最前面**。用户要的是按**内容**改动时间排：
只有案件里的东西（事件 / 页面 / 画布 / 关系图 / 族谱图）变了才往前排，改书名换封面不动。

### 改法

1. `Book` 实体 + `BookResponse`（及 workspace 里的嵌套 book）加一个可空字段：

```java
/** 内容最后改动时间；改书名 / 换封面不刷新它。老数据可空，前端自行回退 updatedAt */
private LocalDateTime contentUpdatedAt;
```

2. **刷新规则**（在对应 service 方法成功落库后，把所属 book 的 `contentUpdatedAt` 置为 now）：

| 会刷新 contentUpdatedAt 的操作 | 不刷新的操作 |
| --- | --- |
| 事件：POST/PUT/DELETE `/api/books/{bookId}/events*`、`PUT /events/{id}`、`PUT /api/books/{bookId}/events/sort` | `PUT /api/books/{id}`（改名 / 封面） |
| 页面：POST/PUT/DELETE `/api/events/{eventId}/pages*`、`PUT /pages/{id}`、`PUT /api/events/{eventId}/pages/sort` | `POST /api/books/{id}/cover`（上传封面） |
| 画布：`PUT /api/pages/{id}/canvas` | `PUT /api/books/sort`（书架手动排序） |
| 关系图：`/api/books/{bookId}/relation-graphs` 增删改、`/api/relation-graphs/{id}` 改名删、`/data`、`/extract` | |
| 族谱图：与关系图同构的 family-trees 全套写接口 | |

   建议收口成一个 `bookService.touchContent(Long bookId)`（update 时把 `contentUpdatedAt = now`），
   在上表左列各写接口成功后调用，避免散落各处漏掉。

3. **不要动原 `updatedAt` 的语义**，两者并存。
4. `GET /api/books`、`GET /api/books/{id}`、`GET /api/books/{id}/workspace` 都要带出该字段；
   老数据为 null 即可，前端会回退 `updatedAt`。

### 数据格式

```json
// GET /api/books 的返回体（节选）
{
  "code": 200,
  "message": "操作成功",
  "data": [
    {
      "id": 1,
      "name": "王某某失踪案",
      "coverType": "color",
      "coverValue": null,
      "coverText": null,
      "sortOrder": 0,
      "createdAt": "2026-09-01T10:00:00",
      "updatedAt": "2026-09-14T16:00:00",
      "contentUpdatedAt": "2026-09-14T15:20:00"
    }
  ]
}
```

### 自测

```bash
BASE=http://localhost:8080/api
# 1. 改书名：updatedAt 变，contentUpdatedAt 不应变
curl -s -X PUT "$BASE/books/1" -H 'Content-Type: application/json' \
  -d '{"name":"新名字"}' | grep -o '"contentUpdatedAt[^,]*'
# 2. 往画布写一笔：contentUpdatedAt 应刷新为当前时间
curl -s -X PUT "$BASE/pages/1/canvas" -H 'Content-Type: application/json' \
  -d '{"background":"plain","objects":[],"relationships":[],"annotations":[],"timelines":[]}' >/dev/null
curl -s "$BASE/books/1" | grep -o '"contentUpdatedAt[^,]*'
```

验收：步骤 1 前后 `contentUpdatedAt` 相同；步骤 2 后 `contentUpdatedAt` 变新；
`updatedAt` 行为与现在完全一致。

### 可以直接发给后端的 prompt

> 请给「推演录」后端的 Book 增加「内容改动时间」字段 `contentUpdatedAt`（可空，LocalDateTime），
> 实体、`BookResponse`（含 workspace 嵌套的 book）都要带出，GET /books、GET /books/{id}、
> GET /books/{id}/workspace 返回它，老数据为 null。
> 刷新规则：事件、页面、画布（PUT /api/pages/{id}/canvas）、关系图与族谱图全套写接口
> 落库成功后，把所属 book 的 contentUpdatedAt 置为当前时间（建议收口成
> bookService.touchContent(bookId) 统一调用）；而 PUT /api/books/{id}（改名/封面）、
> POST /api/books/{id}/cover、PUT /api/books/sort 这三个**不刷新**它。
> 原 updatedAt 语义保持不变。
> 背景：前端书架「按最近编辑」排序要用它——现在按 updatedAt 排，改个书名/封面就把书顶到最前，
> 用户要的是内容（事件/页面/画布/图）改动时间。
> 改完用文档第十节的两条 curl 自测：改书名后 contentUpdatedAt 不变，写画布后变新。

## 十一、用户资料接口 `GET/PUT /api/profile`（本轮新增 · **需要后端实现**）

### 背景

左上角头像点开可自定义展示名（默认「用户」），并预留主题切换（现仅 light，dark / sepia 是占位）。
存储**以后端为唯一权威**：前端读取和保存都走这两个接口；接口未实现期间前端暂用 localStorage
降级兜底（不弹错误），接口一上线自动切换，前端无需再改。

### 接口定义

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/profile` | 读取资料；**无记录时返回默认值**（displayName=「用户」，theme=light），不要 404 |
| PUT | `/api/profile` | 整体保存，upsert |

`ProfileResponse`：

```json
{ "displayName": "沈先生", "theme": "light" }
```

`ProfileUpdateRequest`（PUT 请求体，两个都可空，只传的才改）：

```json
{ "displayName": "沈先生", "theme": "light" }
```

存储建议：单机单用户，建一张 `user_profile` 表（id 固定为 1 的一行，upsert 即可），
两个字段：`display_name varchar(24) not null`、`theme varchar(16) not null default 'light'`。
校验：displayName trim 后非空、≤24 字符；theme 是短字符串，后端不枚举（前端把关，原样存取）。

### 数据格式

```json
// GET /api/profile（无记录时）
{ "code": 200, "message": "操作成功", "data": { "displayName": "用户", "theme": "light" } }

// PUT /api/profile 的返回
{ "code": 200, "message": "操作成功", "data": { "displayName": "沈先生", "theme": "light" } }
```

### 自测

```bash
BASE=http://localhost:8080/api
curl -s "$BASE/profile"                                   # 首次：返回默认值
curl -s -X PUT "$BASE/profile" -H 'Content-Type: application/json' \
  -d '{"displayName":"沈先生","theme":"light"}'
curl -s "$BASE/profile"                                   # 读回必须是沈先生
```

### 可以直接发给后端的 prompt

> 请给「推演录」后端新增单用户资料接口：GET /api/profile 与 PUT /api/profile，
> 统一 Result 包装。字段只有两个：displayName（展示名，默认「用户」，trim 后非空、≤24 字）、
> theme（主题标识，默认 light，字符串原样存取）。GET 无记录时返回默认值而不是 404；
> PUT 做 upsert（建议 user_profile 表固定 id=1 一行）。不用做登录鉴权，单机单用户。
> 背景：前端左上角头像可自定义名字并预留了主题切换，先用 localStorage 兜底，
> 接口就绪后自动切到后端。改完用文档第十一节的三条 curl 自测。
