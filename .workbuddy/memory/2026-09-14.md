# 2026-09-14 · Detective Helper 打包落地

## 背景

推理笔记（推演录）原本设想 JavaFX 壳 + WebView + **GraalVM native-image** 打包，
但 GraalVM 与 WebView 冲突（WebView 依赖 WebKit，native-image 不支持）。改为
**jpackage + Spring Boot fat jar** 路线。

用户确认的四项决策：
- 应用正式名：**Detective Helper**（exe 名 / 安装目录 / 快捷方式 / 卸载注册表项）
- 范围：打包 + Lombok + MyBatis 重构（全量）
- 数据目录：**安装目录/data**（便携；不可写时降级 `%LOCALAPPDATA%/Detective Helper/data`）
- 交付：免安装 zip + exe 安装包，两者都要

## 关键技术结论（踩过的坑）

### 1. JavaFX 在 classpath 模式下必须由 JarLauncher 启动
jpackage 的 `--main-class` **必须是** `org.springframework.boot.loader.launch.JarLauncher`，
不能写 `DesktopApplication`。JDK 启动器一旦发现「主类是 `javafx.application.Application`
子类 + JavaFX 在 classpath 上」就直接拒绝启动，报
`JavaFX runtime components are missing`。由 JarLauncher 反射调 main() 可以绕过该检查。

### 2. jpackage 的 runtime 里**没有** java.exe
jpackage 走 jlink 的「运行时镜像」，按设计**不含** `bin\java.exe` / `javaw.exe`：
`runtime\bin` 下只有 `jli.dll`，JVM 本体在 `runtime\bin\server\jvm.dll`。
所以：
- 校验 runtime 有效性要看 `server\jvm.dll` + `runtime\release` 的 `MODULES=`，不要找 java.exe
- 想用这份裁剪 JRE 跑任意 main，得临时从同版本 JDK 复制 `java.exe` 进去（冒烟测试阶段一就这么干）

### 3. 后端必须产出普通 jar
`spring-boot-maven-plugin` 的 `repackage` 在 backend 绑 `phase=none`，
只有 desktop 产出 fat jar（finalName `DetectiveHelper-desktop`）。

### 4. 前端产物并入路径
backend 的 maven-resources-plugin 把 `../frontend/dist` 复制到
`${project.build.outputDirectory}/static`（必须 `targetPath=static`）。
结果是 `static/` 在**嵌套的 backend jar 内部**，不在 desktop fat jar 顶层 —— 校验时要注意。

## 环境相关的三个硬坑（PowerShell 工具链）

### A. `.ps1` 必须 UTF-8 **with BOM**
PowerShell 5.1 读无 BOM 的 UTF-8 中文脚本会按 GBK 解析，报
「字符串缺少终止符」之类的解析错误，而且**不报行号以外的线索**。
本仓库 scripts/*.ps1 全部按 UTF-8 with BOM 保存。用 Write 工具新建后要补 BOM。

### B. `$ErrorActionPreference='Stop'` + 原生程序 stderr = 终止性 RemoteException
`_common.ps1` 顶部设了 `Stop`。PS 5.1 在「原生程序往 stderr 写 + 输出进管道/重定向」时
会把普通 stderr 输出升级成终止性错误，抛 `System.Management.Automation.RemoteException`
（Message 还是空的，极难查）。Maven 打一行警告、vite 打一行进度就会整个中断。
→ 所有原生调用（mvn / jar / jpackage / tar / candle）统一走 `Invoke-DhaNative`，
   里面临时把 ErrorActionPreference 降成 `Continue`。

### C. 宿主的 safe-delete 钩子把删除改道回收站，且是**异步**的
`Remove-Item` 会抛
`[safe-delete][SAFE_DELETE_FAIL_CLOSED] {"reason":"trash-failed","detail":"OK <path>"}`
—— detail 是 "OK"，东西确实进回收站了，纯属误报；而且搬运是后台进行的
（实测 250MB / 200 文件的 app-image 约 3 秒后才真正消失）。
→ 统一用 `Remove-DhaPath`：吞掉误报 + 轮询等路径消失（默认 30 秒超时）。
   副作用：每次重建都会把上一份 app-image 推进回收站，回收站会变大。

## 离线字体决策

`frontend/index.html` 原来 `<link>` 到 fonts.googleapis.com。桌面版跑在 JavaFX WebView 里，
`<head>` 的外链样式表会**阻塞首屏渲染** —— 断网时白屏十几秒，单机应用不可接受。
→ 移除外链，字体栈改为纯本地（`src/styles/tokens.css`）：

- 宋体档：思源宋体 → Noto Serif SC → Songti SC → **华文中宋**（本机没装思源，用华文中宋而不是 SimSun）
- 黑体档：思源黑体 → Noto Sans SC → PingFang SC → **微软雅黑**
- 等宽档：Sarasa Mono SC → Noto Sans Mono → **Consolas**

精确到设计稿的 Noto 字体用 `scripts/fetch-fonts.ps1` 可选镜像（CJK 分片很多，约 15~25MB）。

### D. 【新】宿主环境里存在"只有大小写不同"的重复环境变量 → `Start-Process` 必死

这台机器的父进程环境块里同时有 `HTTPS_PROXY` / `https_proxy`、`HTTP_PROXY` / `http_proxy`、
`Path` / `PATH` 三对。`Start-Process` 把当前环境往**大小写不敏感**的 StringDictionary 里塞，
第二项必然撞键，抛：

```
已添加项。字典中的关键字:"HTTPS_PROXY"所添加的关键字:"https_proxy"
```

三个要命的特征：
1. 它是**在 cmdlet 参数绑定阶段**炸的，既不是 terminating error 也进不了调用方的 `try/catch`；
2. **同一脚本里的 `&` 原生调用完全正常**（`&` 不碰环境字典）—— 所以极容易被误判成脚本逻辑问题；
3. `Get-ChildItem env:` 和 `$env:X` 都是大小写不敏感的，**看不见**这种重复项；
   要发现得用 `[System.Environment]::GetEnvironmentVariables()` 按 `ToLowerInvariant()` 分组找 `Count -gt 1`。

→ `_common.ps1` 新增 `Remove-DhaDuplicateEnvKeys`：把每种大小写写法都置空（Windows 下
  `SetEnvironmentVariable` 按名查找不分大小写，同名多变体会被一起清掉），再写回一份规范副本
  （`PATH` / `HTTP_PROXY` / `HTTPS_PROXY`）。只影响本进程。smoke-test 开头调用（本次修了 3 组）。

### 连带修正：`Start-Process` 必须放进 `try` 内
第一次跑 smoke-test 时，阶段一在 `Start-Process` 那行就死了，导致 `finally` 没执行、
临时注入的 `runtime\bin\java.exe` 残留在 app-image 里（下次打包会被当产物塞进 zip）。
→ 把 `Start-Process` 移进 `try`，让 `finally` 无论如何都能撤掉临时启动器。

### 关于卸载器的一个事实修正
`make-installer.ps1` 原来写「卸载程序会问要不要保留 data」—— **这是错的**。
jpackage 生成的卸载器**不询问**，它会连同 `INSTALLDIR` 一起删掉，`data/` 在里面一起没。
数据放安装目录本身就意味着"卸载 = 丢案件"。已把脚本收尾提示改成明确警告：
想留案件先拷走 data。这条也回写进了打包技能。

# 第二轮：用户实机反馈六个问题

用户装完后报了六个问题：① 启动遮罩的加载文字与提示错位（不居中）；② 已有案件之后「新建案件」卡片被压扁；
③ **时间线选不了时间**；④ 原生下拉框太"系统"、不好看；⑤ 外壳让页面被压缩且**模糊**；⑥ 操作**卡**。

## 已修：前端三处（浏览器/Electron/Tauri/JavaFX 四种方案通用）

### 1. 「新建案件」被压扁 —— 是 `<button>` 在 WebKit 下不做网格拉伸
`BookshelfView.vue` 的 `.create-slot` 是 `<button>`，网格 201px 固定列。
**WebKit 不给 `<button>` 应用 grid 的 `stretch`**，宽度退化成内容宽度（实测约 51px）；
空状态用的是 `.empty-ghost`（有显式 `width: 201px`），所以只有"已有案件之后"才暴露。
→ 给 `.create-slot` 补显式宽度 + `justify-self: stretch`。

顺带确认了一件反直觉的事：截图里第一张卡 303 物理像素 = CSS 201px、间距 32 = 22px，
即截图是 **1.5 倍缩放**，网格本身没写错 —— 别被"数字对不上"误导成布局 bug。

### 2. 时间线选不了时间 —— 原生 `datetime-local` 在 WebView 里根本不可用
`TimelinePanel.vue` 原来用 `<input type="datetime-local">` / `type="date"`。
Chrome 会弹系统选择器，**JavaFX 的 WebKit 不支持这两个类型**：不弹选择器、也不接受手输。
→ 换成 antd `<a-date-picker>`（纯 JS/CSS，不依赖系统控件）。
Draft 里仍是 `'YYYY-MM-DDTHH:mm'` 字符串，中间垫一层 `computed` 做 dayjs ↔ 字符串换算，
`submit` / `canSubmit` / `normalizeDateTime` 一律没改。

### 3. 8 处原生 `<select>` → `<a-select>`
`TimelinePanel.vue` 2 处 + `BookWorkspaceView.vue` 6 处。主题令牌集中在 `App.vue` 的
`a-config-provider :theme`（antd 4 走 CSS-in-JS），主色对齐 `tokens.css` 的 `#7C9A88`。
踩点：antd 只有拿到 `undefined` / `null` 才显示 placeholder，而原来 `edgeDraft.source` 初值是空串
→ 要垫一层 `'' ↔ undefined` 转换，否则占位符不显示。

同类细节：`TimelinePanel` 的头部拖动判定原本只排除 `input/button/select`，
antd 的触发区是 `div` → 必须把 `.ant-select` / `.ant-picker` 也加进去，否则点下拉框空白处会把整条时间线拖走。

## 已修：antd 全量引入 → 按需注册（对"卡"有直接贡献）

`main.ts` 原来是 `app.use(Antd)`，实测 antd 块 **1405 KB / gzip 415 KB**。
本项目模板只用到 4 个组件（ConfigProvider / Select / SelectOption / DatePicker）
—— `Modal` / `message` 是散落各处的具名导入，本身就能 tree-shake，不需要全局挂载。
→ 改成 `app.component(...)` 逐个注册。
**结果：439 KB / gzip 132 KB，降 69%。**

WebKit 每次启动都要把这 1.4 MB 完整解析一遍，这是"操作很卡"最直接的一个来源。
另：`dayjs/locale/zh-cn` 要单独引 —— ConfigProvider 的 locale 管选择器面板文案，
weekStart / 星期名由 dayjs 自己的 locale 决定，两者不能互相替代。

## 实测诊断：模糊与卡顿的根因（JavaFX 路线）

用 `java -Dprism.verbose=true -Djavafx.verbose=true -jar DetectiveHelper-desktop.jar` 采集：

| 项 | 实测 | 结论 |
|---|---|---|
| Prism 管线 | `Prism pipeline init order: d3d sw` → `Initialized prism pipeline: com.sun.prism.d3d.D3DPipeline`，`D3DPipelineManager: Created D3D9Ex device` | **GPU 加速正常**，不是软件渲染回退 → 「强制 d3d」这条免费午餐不存在 |
| HiDPI | `Opting in for HiDPI pixel scaling` | JavaFX 自己在按 1.5x 渲染，所以**外壳本身不糊**；糊在 WebView 内部，是 WebKit 自己的渲染 |
| 启动 | `Started application in 12.279 seconds (process running for 19.295)` | ⚠️ 后端冷启动 12.3 秒 —— 这是"启动慢"，**与换不换外壳无关** |

模糊对应的 JDK 缺陷是 **JDK-8252649**：Windows 在 125%/150%/175% 缩放下，
WebView / 带滚动的列表会发虚，100% 和 200% 正常。用户屏幕 2560×1600 正好落在 150%。

另有一个观察到但**未构成问题**的现象：JavaFX 原生库藏在 Spring Boot 胖 jar 的嵌套 jar 里，
`NativeLibLoader` 反复刷 `Invalid URL for class: jar:nested:/.../javafx-graphics-21.0.3-win.jar!/...`，
退回"从资源解压"（`Loaded library /prism_d3d.dll from resource`）。
但核查 TEMP 后**没有**发现被解压的 `jfxwebkit.dll`，所以不构成"每次启动解压上百 MB"的负担 —— 别误判。

## 环境事实（决定外壳选型）

| 项 | 结果 |
|---|---|
| Node / npm | ✅ 22.22.2（托管版） |
| Rust / cargo | ❌ 未安装 |
| VS BuildTools | ❌ 无（`vswhere.exe` 不存在） |
| WebView2 Runtime | ✅ 已装，pv=152.0.4191.66 |
| GPU | NVIDIA RTX 5050 Laptop + AMD Radeon 610M（双显卡） |
| 屏幕 | 2560×1600（典型 150% 缩放面板） |

→ **Tauri** 运行前提满足，但要先装 Rust + MSVC 生成工具（数 GB）。
→ **Electron** 无新工具链，Node 现成。

## 待决：外壳是否换掉（用户主动提出）

用户原话：*「如果JavaFx性能不好，也可以换成Electron，或者Tauri等等，只要能完美的表出画面质量和不卡顿就行」*。

我的判断：JavaFX WebView 是旧版 WebKit，正是"模糊 + 卡 + 不支持 `datetime-local`"这一切的共同根源。
换 Chromium 系外壳后**画面质量由构造保证**，因为用户在浏览器里看到的参照物就是 Blink 渲染的。
但**换外壳治不了 12 秒启动**，那是 Spring Boot 的账，属另一件独立的事。

已捕获的关键事实：`MainWindow.bootBackendAsync()` 里 `awaitHttpReady` 打的是
`BackendServer: 后端服务已就绪: {url}`，smoke-test 阶段二靠这行解析端口 —— 改外壳时这行语义不能动。

# 第三轮：用户确认换 Electron + 一起治启动

用户拍板：**换 Electron**，并且**一起优化 Spring Boot 冷启动**。

## 换壳的收益账（先把账算清楚，别把两件事混起来）

- 「画面质量 / 卡顿」← 由 **Chromium** 解决，与 GraalVM 无关。
- 「启动慢」← 这才是 GraalVM 的地盘，而且换 Electron 本身**不**治它。

## 关于 GraalVM（用户主动问的，结论留档）

换 Electron 后 **确实可以用 GraalVM 了** —— 挡住 native-image 的从来是 JavaFX WebView 的
WebKit 原生库，不是 Spring Boot。Java 侧退化成纯无界面 HTTP 服务后，正是 native-image 的甜点区。

依赖侧的实际情况（实测拆包确认）：

| 依赖 | 自带 native-image AOT 提示 | 结论 |
|---|---|---|
| Spring Boot 3.3.4 / Tomcat / Jackson | ✅ | 开箱可用 |
| sqlite-jdbc 3.45.x | ✅ 含 `org.sqlite.nativeimage.SqliteJdbcFeature` + `META-INF/native-image/.../native-image.properties` | 官方支持 |
| **MyBatis 3.5.14 / mybatis-spring / 其 boot starter** | ❌ **一个都没有** | 死角，反射+动态代理要手工声明 |

**但入场费很贵，而且本机付不起**：native-image 在 Windows 上必须用 MSVC 链接（`cl.exe`/`link.exe`）。
实测本机 **没有 VS、没有 Windows SDK、`vswhere.exe` 不存在、没有 GraalVM** —— 数 GB 工具链，
和「为了 Tauri 要装 Rust」是同一笔开销，且 MyBatis 那关要来回几轮（反射错误往往运行时才炸）。
另外 native-image **没有 JIT**，长时间运行吞吐通常低于 JVM，别当「全面更快」。

**结论：暂不上 GraalVM。** 先打便宜的牌（展开 classpath + 无 JavaFX），它仍是后续可选增量步骤。

## 已落地：后端运行形态改造（Electron 不需要 JavaFX，也就不需要胖 jar）

- `backend/pom.xml` 新增 `maven-dependency-plugin:copy-dependencies`（prepare-package，includeScope=runtime）
  → 依赖平铺到 `backend/target/lib`。启动方式变成
  `java -cp "target/classes;target/lib/*" com.theos.detectivehelper.DetectiveHelperApplication`，
  **绕开 Spring Boot 的 BootLoader**。
- 顺带修掉一个真缺陷：`copy-resources` 只覆盖不删除，而 Vite 产物文件名带内容哈希，
  于是 `target/classes/static` 会一轮轮攒下旧文件（实测同时存在 439KB 与 1405KB 两代
  `ant-design-*.js`，都会被打进发布包）。→ 新增 `maven-clean-plugin` 在 prepare-package
  先清 `target/classes/static`，让 `package` 变成幂等的。

### 实测对比（HTTP 健康探测判定就绪，每次先删 app.log）

| 配置 | 启动 → 就绪 | 上下文初始化 |
|---|---|---|
| 旧：胖 jar + JavaFX（冷启动） | 19.8 s | 4889~6766 ms |
| 新：展开 classpath，无 JavaFX | **7.4 ~ 8.2 s**（3 次：8.2/7.4/7.6） | 2707~3067 ms |

即：**去掉 JavaFX 省掉约 7 秒，展开 classpath 再让上下文初始化快约 40%。**

## ⚠️ 最大的坑：`-XX:+AutoCreateSharedArchive` 在这个场景下是**毒药**

我一度在 Electron 的 spawn 里加了 AppCDS：
`-XX:+AutoCreateSharedArchive -XX:SharedArchiveFile=<data>/app.jsa`。实测结果：

| 标志 | 启动 → HTTP 200 |
|---|---|
| 无 | **7.5 ~ 8.0 s** |
| 带上面两行 | **47.5 ~ 48 s**（上下文初始化 3.0s → 17.6s） |

而且是**每一次都慢**：Windows 上 `child.kill()` 走的是 `TerminateProcess`，JVM 拿不到
优雅退出机会，CDS 归档**永远写不出来**（实测 `app.jsa` 始终不存在）→ 每次启动都白付罚款。

这个坑还带出一个诊断教训：我最初把 23s / 28s / 31s / 40s 的 Electron 启动耗时

## 测方法学（这次被自己坑过，务必遵守）

1. **判定就绪别用日志正则**：展开 classpath 后日志文案是

# 第四轮：用户验收 Electron 版（启动仍偏慢 + 竖向时间轴两个新 bug）

用户实测后的三段反馈：① 开始还是有点慢；② 竖向时间轴时时间标识（如 `9/11 23:11`）
**前半截被裁掉**；③ 时间段的**尾部时刻不显示**。

## 已修 1：竖向刻度被裁 —— 左侧留白是写死的 66px

`TimelinePanel.vue` 里 `axisVX = 66` 是常量，而刻度以 `axisVX - 10 = 56` 右对齐。
`9/11 23:11` 这种 10 字符刻度按等宽字体约 53~58px 宽（本机没装 Sarasa Mono 会落到
Consolas，0.55em → 约 58px），再加 `.tl-tick` 那层 3px 白色光晕的描边 ——
**左边缘越过 x = 0，被 SVG 视口直接切掉开头**。
`12/31 23:59` 这种 11 字符的更明显。

→ 改成**实测**：模板里放一个不可见、不占位的探针 `<span class="tick-probe">`
（同 `--font-mono` / 同 10.5px），脚本喂进当时可见的每条刻度文案量最宽的那条，
再倒推 `axisVX = max(66, 宽度 + 14)`。刻度短时取值仍是 66，视觉位置不变。

**关键陷阱**：探针必须用 `offsetWidth`，不能用 `getBoundingClientRect()`。
面板挂在 `.stage` 的 `transform: scale(zoom)` 里，`getBoundingClientRect()` 给的是
**缩放后**的视觉尺寸 —— 画布缩小到 0.6 就会把刻度量窄、留白算少，等于换个方式重犯原 bug。

顺手治了同族的第二处：纵向刻度分道是**往下推**的（`tickRow * 14`），靠底部的点被推出去
就掉出 SVG 视口（纵向 SVG 高度由面板高度决定，不像横向能自己长高）。
新增 `vTickY(pos, row)`：算出来的基线一旦越过底边就退回自己那一行 —— 挤一点，但看得见。

## 已修 2：时间段只有起点刻度

`timelineLayout.ts` 只产出 `tick`（起点），终点那个位置画了空心小圆点却没有时刻文字，
于是「从 20:00 到什么时候」在轴上读不出来。

→ 给 `LaidOutPoint` 加 `endTick` / `endTickRow` / `endTickHidden`，
并把**起点刻度与终点刻度放进同一套去重 + 分道**里（按 px 升序排，同位置时起点在前）。
否则「前一段的终点」与「后一点的起点」会各自以为自己唯一，叠在同一行。
横向纵向都要渲染。

## 启动：`-XX:TieredStopAtLevel=1` 省下 2.9 秒

立了可复用的基准脚本 `build/bench/bench-startup.ps1`（同一 classpath、每个组合跑 3 轮取中位数、
每轮先删 `-wal`/`-shm`、数据目录隔离到 `build/bench/data`，主指标取日志里
`process running for` 而不是我自己的秒表）。
**必须把 JVM 参数与应用参数分开传** —— `--spring.*` 塞到主类之前 JVM 直接
`Unrecognized option` 起不来（我第一次就踩了这个，"lazyinit 全 FAILED"）。

| 组合 | 进程启动 → 就绪（中位数） |
|---|---|
| 无标志 | 6.94 s |
| **`-XX:TieredStopAtLevel=1`** | **4.00 s** |
| + `-XX:+UseSerialGC` | 4.03 s（无收益） |
| + `-Xms96m -Xmx512m` | 6.70 s（无收益） |
| + `-Dspring.jmx.enabled=false` | 3.96 s（噪声内） |
| + `--spring.main.lazy-initialization=true` | 3.69 s（省 0.3s，但只是把代价搬到首次请求，且会推迟建表/迁移，不值） |

TieredStopAtLevel=1 的语义是「只用 C1 **且不做 profiling**」——Spring 启动要跑掉几千个
大多只执行一两次的方法，为它们收 profile 纯属白花时间。这是省下 2.9 秒的真因。
代价是热点方法不被 C2 极致优化；本应用重活是 SQLite + JSON，都是 I/O 与分配主导。
已在 `main.js` 注释里写明"若将来出现 CPU 密集卡顿（如超大关系图最短路）先去掉这行重新量"。

另外把健康探测间隔 200ms → 100ms（直接换算成启动耗时的一部分）。

**已用 `build/bench/verify-with-flag.ps1` 验证**：带生产参数启动，`/api/health`、`/api/books`、
`/api/profile`、`/`、`/bookshelf` 全 200，POST 建案件 + 读回也通 ——
加速没有换成运行期异常。

## AppCDS：这条路线**彻底判死**（结论已写进 main.js 注释）

原来留下的注释说「以后要上 CDS 得构建期生成归档 + 只读使用」。这次真去做了，发现也不通：

**动态归档不允许 classpath 上存在非空目录**，JVM 直接拒绝启动：
```
[error][cds] Error: non-empty directory '<...>\backend\target\classes'
Error occurred during initialization of VM
Cannot have non-empty directory in paths
```
而我们为绕开 Spring Boot 嵌套胖 jar 的 BootLoader，用的恰恰就是这个展开目录。
想用 CDS 就得把应用类重新打成 jar，等于拿展开 classpath 的收益去换一个更小的收益 —— 不值。
（顺带记下：训练运行用 `--spring.main.web-application-type=none` 能让 main() 自然返回、
优雅退出，这是绕开"Windows 上 kill 是 TerminateProcess、归档写不出来"的正解，
只怪 classpath 这一关过不去。）

# 第五轮：启动再压一半（并行 spawn + 全 jar classpath + CDS 复活）

用户反馈：「都 ok，启动体感是还是要加载 3-4s」。于是把启动这条线重新量了一遍。

## 结论先行：端到端 4.6 秒 → 3.6 秒，JVM 段 3.8 秒 → 2.8 秒

所有数字都是同机、轮转（round-robin）取中位数，单位是「Electron 进程启动 → 目标就绪」。

| 阶段 | 端到端 | 其中 JVM 段 |
|---|---|---|
| 起点（展开目录 / 不提前 spawn / 无 CDS） | ~4619 ms | ~3820 ms |
| + 提前 spawn（与 Chromium 初始化并行） | ~4390 ms | ~3710 ms |
| + 全 jar classpath + CDS | **~3600 ms** | **~2830 ms** |

独立测 JVM 时（`bench-cds-jar.ps1`）是 3.97 → 3.36 → 2.06 秒；放进外壳里只兑现到 2.83 秒
（差额怀疑是前 0.2 秒内与 Chromium 剩余初始化争用）。**这个差额还没查，值得回头量。**

## 教训一：不做轮转就会量出反向结论

第一次测「提前 spawn 到底有没有用」时，我是「一组连着跑 3 轮再换下一组」，
结果得出 **并行反而慢 470ms**，差点把改动回滚。改成交替跑（c1/o1/c2/o2）后：
对照 4690/4547，并行 4404/4376 —— **并行快约 230ms，方向上是对的**。

差别全在机器负载漂移：逐组跑时，「并行」那组恰好落在机器更忙的两分钟里。
→ **凡是 A/B 对比，一律轮转。** 这条已经写进 `bench-cds-jar.ps1` 的注释里。

判据：`外壳进程启动到此` 在并行组是 467ms、对照组是 660ms，差 193ms，与端到端差 230ms 吻合 ——
**改动的收益可以自证**，这是判断「测得对不对」最有力的交叉验证。

## 教训二：「jar 比展开目录快」——推翻了 pom 里的老注释

`backend/pom.xml` 里原话是「展开成 target/lib + target/classes 之后直接用 java -cp 启动，
绕开 BootLoader，冷启动明显更快」。这次实测三种形态：

| 形态 | JVM 启动 → 就绪 |
|---|---|
| 展开 classes 目录 | 3.97 s |
| **普通 jar + lib\*** | **3.36 s** |
| Spring Boot 嵌套 fat jar | （更慢，当初就是因为它才改的） |

两件事可以同时成立：嵌套 fat jar 要经 BootLoader 解压偏移量，**那是最慢的**；
而普通 jar 内部有索引、可内存映射，比让 JVM 逐个 stat/open 上百个 class 文件更快
（Windows 上还要过一遍杀毒扫描）。**真实顺序：嵌套 fat jar > 展开目录 > 普通 jar。**

## 教训三：CDS 不是走不通，是我上次把两件事混成一件

第四轮我判了「AppCDS 彻底判死」，写进了 main.js 注释。**那个结论错了一半**，这次纠正：

| 障碍 | 上次的判断 | 这次的做法 |
|---|---|---|
| 归档要在 JVM **正常退出**时才写 | ✅ 真的（`child.kill()` = TerminateProcess） | 训练用独立进程 `CdsTrainingEntry`，跑完自己 `System.exit(0)` |
| 动态归档**不允许 classpath 上有非空目录** | ✅ 真的，但**有解** | 应用类打成**普通 jar**，classpath 只剩 jar |

两条都解决后：**3.97 s → 2.06 s**（独立测），`-Xshare:on` 强校验通过。

### 关键细节：训练入口必须打进同一个 jar

CDS 会校验运行期的 classpath 与训练时是否一致。把训练入口放在旁边一个目录里，
classpath 立刻多出一个目录 → 归档被拒。所以 `CdsTrainingEntry` 只能放 `src/main/java`，
代价是这个类会随包发布（不被任何东西引用，无副作用）。

### ⚠️ 最大的隐藏陷阱：CDS 按 jar 的**时间戳**校验

```
A jar file is not the one used while building the shared archive file: ...app.jar
...app.jar timestamp has changed.   →   Unable to use shared archive.
```

- **内容一字不改、只是文件被重写**，归档一样作废；
- 而且 `-Xshare:auto` 是**静默回退**——启动悄悄慢 1.3 秒，**没有任何报错**。

所以：`app.jsa` 的指纹必须用 **size + mtime**，不能用「内容哈希」；
`run-electron-dev.ps1` 里也是靠"只在 jar 真的更新时才 Copy-Item"来避免无意义地废掉归档。

### 训练耗时 50 秒，但**不是**磁盘的锅

隔离实验：不带应用 1.1s（归档 0.56MB）、非 web 模式 34.7s（36MB）、完整 49s（44MB）。
`-Xlog:cds=info` 显示真正写盘只占 **0.06 秒**（48.697s → 48.758s 写完 44MB），
慢的是落盘**之前**的处理阶段，且与归档体积成正比。本机磁盘实测 640 MB/s。
→ 这是动态归档的固有开销，策略就是**构建期生成一次、随包发布**，
开发期指纹一致自动跳过（1 秒），急用时 `-SkipCds`。

  （`jpackage --runtime-image`），要么在打包后另想办法训练。见任务 #19。

## 环境/工具的坑（补充）

1. **沙箱的 `Remove-Item` 是 safe-delete 且会 fail-closed**：路径不存在、或回收站不可用时，
   直接抛 `SAFE_DELETE_FAIL_CLOSED`，**连 `-ErrorAction SilentlyContinue` 都拦不住**。
   构建脚本里删文件改用 `[System.IO.File]::Delete()`；`Start-Process` 的重定向本身会截断，
   干脆不删。
2. **`Get-Content` 默认按 ANSI 读 → 中文日志全乱码**：`shell.log` / `app.log` 是 Node/logback
   按 UTF-8 写的，读它们必须显式 `-Encoding UTF8`。我第一次的基准脚本就是因此
   让"后端就绪""外壳进程启动到此"两条中文正则永远匹配不上（安静地返回 -1，不报错）。
3. **`"$Label: 文字"` 会被解析成盘符变量**：`$Label:` 里冒号触发 drive 语法，要写 `${Label}`。
4. **`$ErrorActionPreference='Stop'` + 原生 stderr**：`javac` 打一行"注: 启用了注解处理器"
   就会让脚本死在无关紧要的提示上。`Invoke-DhaNative` 之外的原生调用统一走
   `Start-Process -RedirectStandardOutput/-RedirectStandardError`，不要用 `& ... 2>&1`。
5. PowerShell 工具在本机不回传 stdout，**且命令会因 `.ssh` 被沙箱拦下**（原因不明，
   `scripts/` 里没有任何 `.ssh` 引用）—— 拦下时不要重试，把结果落到文件再读。
