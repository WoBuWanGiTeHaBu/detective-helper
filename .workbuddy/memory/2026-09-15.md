## 「提前 spawn」对照实测：保留，不回滚（8 轮，交替跑，避开负载漂移）

| 组 | Chromium 初始化→boot() | JVM 段(就绪-初始化) | 总计 |
|---|---|---|---|
| 串行 c1 / c2 | 449~458 ms | 2580~2701 ms | 3547 / 3559 / 3641 / 3669 |
| 并行 o1 / o2 | 227~230 ms | 2580~2650 ms | 3354 / 3361 / 3371 / 3863* |

（*o2 run2 = 3863 ms 为离群值；同组其余三次 3354~3371 高度一致）

**结论一：并行仍划算，约省 240 ms，且不付任何代价。**
`Chromium 初始化 → boot()` 从 453 ms 降到 228 ms（省下的正是串行白等的那段），
而 **JVM 段在并行与串行下几乎完全相同**（中位 2618 vs 2623 ms）。

**结论二：上轮「715 ms 差额是并行争 CPU」的怀疑被证伪。**
串行下 JVM 段一样慢，说明与并行无关。差额的真正来源是**度量口径不同**：
- 独立基准（`bench-startup.ps1`）读 JVM 自报的 `process running for X`，**从 main() 起算**；
- 外壳基准（`bench-shell.ps1`）测「spawn → HTTP 探到就绪」，**包含** java.exe 进程创建 + JVM 引导 +
  探测轮询间隔（100 ms 间隔 → 平均 ~50 ms 延迟）。

这部分是固定成本，靠调参压不动。**启动优化到此收束**：端到端并行 + CDS 约 3.35 s。

## 打包链路打通（jlink + CDS + electron-builder）

### 新增 `scripts/stage-runtime.ps1`（四步，顺序不能换）

1. **jlink 裁 JRE** → `build/stage-jvm/jre`（20 模块，含基础 CDS 归档后 **83.7 MB**）
   模块表刻意不含 JavaFX 专用的 `jdk.jsobject` / `jdk.xml.dom`（WebView 时代遗留）。
2. **组装** → `build/stage-jvm/app/{app.jar, lib/*.jar}`（53 个依赖）
3. **实起验证**：用裁剪 JRE 真起后端并打 `/api/health`。这一步是模块表的验收 ——
   jlink 少带模块的症状是**运行期** NoClassDefFoundError，打包时完全不报错。
4. **用裁剪后的 JRE 训练 CDS** → `build/stage-jvm/app/app.jsa`（43.1 MB）

产物结构与 `electron/main.js` 一一对应：`resources/jre` + `resources/app/{app.jar, lib, app.jsa}`。

### ⚠️ 踩到的关键陷阱：jlink 默认不生成基础 CDS 归档

```
[warning][cds] -XX:ArchiveClassesAtExit is unsupported when base CDS archive is not loaded.
```

- 动态归档是**叠在基础归档（classes.jsa）之上**的，而 jlink 默认**不生成**它
  （源 JDK 有 `bin/server/classes.jsa`，裁出来的 JRE 里没有）。
- 症状极具误导性：**只有一条 warning**，JVM 照常起完应用、训练进程照常打印
  `CDS_TRAIN_READY`，但归档永远不生成 —— 白等 50 秒只得到"归档没有生成"。
- 修法：jlink 加 `--generate-cds-archive`（已加，并把它纳入 stage 指纹，
  否则改了选项却因"指纹一致"跳过裁剪，问题依旧）。
- 另在 `make-cds-archive.ps1` 加了前置检查：基础归档缺失时**提前失败**（省 50 秒）
  并把修法写进错误信息。

### 打包脏点（已修）

`make-cds-archive.ps1` 把训练日志/校验日志/指纹文件写在归档**旁边**，
而那个目录整个进包 → 包里多出 15 KB 日志（含构建机绝对路径）。
两处修：`stage-runtime.ps1` 训练后 `Clear-CdsNoise` 清理；
`package.json` 的 extraResources 加 `filter: ["**/*","!*.log","!*.err","!*.meta"]`。

### 卸载时的数据保留策略（决策，别改错）

数据在**安装目录\data**（`resolveAppDir` 的 dir/portable 分支），不在 AppData，
所以 `deleteAppDataOnUninstall:false` **救不了它**。

新增 `electron/build/installer.nsh`（`nsis.include` 引入），`customUnInstall` 里：
- `data\` 非空 → MessageBox 询问「保留 / 删除」
- **保留 = 原地不动**，刻意不移动 —— 升级时 NSIS 会先跑一遍卸载流程，
  若把 data 移出安装目录，新版本就再也找不到旧数据（那才是真事故）。
- 删除 = `RMDir /r "$INSTDIR\data"`

### ⚠️ portable 每次启动要自解压 ~20 秒（选型结论）

| 形态 | 墙钟 | 内部（Electron 计时） |
|---|---|---|
| `portable.exe` | **23.2 ~ 24.3 s** | 3420 ms |
| `win-unpacked`（等价 NSIS 安装版） | —— | **3294 ms** |

electron-builder 的 portable 是 7z 自解压包，**每次运行**都把约 300 MB 解压到
`%TEMP%\<随机名>\`，光解压就约 20 秒（第 1、2 次分别是 24.31 / 23.17 s，没有缓存效应）。
**结论：portable 不能作为日常使用形态，日用应装 NSIS 安装版**（安装时解压一次，之后 ~3.4 s）。

顺带验证到：从 `%TEMP%` 的解压目录运行时，日志仍显示 `CDS: 启用（app.jsa）` ——
说明 7z 解压**保留了** jar 的 mtime，CDS 在 portable 形态下也是有效的。

### 这次踩到的新坑（都值得记住）

1. **jlink 的 `classes.jsa` 是只读文件。**
   `--generate-cds-archive` 产出的 `jre\bin\server\classes.jsa` 与 `classes_nocoops.jsa`
   带只读位，`.NET Directory::Delete` 删它抛「对路径 … 的访问被拒绝」，
   而**报错完全不提只读**，看起来像文件被占用，极容易往错方向排查。
   `stage-runtime.ps1` 的 `Remove-Hard` 已改为先递归清只读位再删。
   → 以后凡是要删 jlink 产物或 CDS 归档的脚本，都得这样处理。

2. **vite 清空 dist 会被本机 safe-delete 的批量守卫拦下。**
   报 `[SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":1159,"threshold":50}`，
   因为宿主把 `CODEBUDDY_*` / `GENIE_*` 环境变量继承给了 Maven → npm → vite 子进程。
   跑构建前把这些 env 变量清掉即可。**用户自己的普通终端没有这个问题**，
   所以不要把规避写进项目脚本。

3. **electron-builder 的 zip target 不套顶层目录。**
   解压出来 300 多个文件散在同一层。`build-release.ps1` 新增 `Add-ZipRootFolder`，
   统一套一层 `Detective Helper/`（不用 `CreateFromDirectory(includeBaseDirectory)`
   是因为那会拿 `win-unpacked` 当目录名，改名它会让下次构建多解压一次 Electron）。
