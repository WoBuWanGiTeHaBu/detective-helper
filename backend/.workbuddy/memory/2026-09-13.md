## 修复后端编译错误（EventService / PageService / RelationGraphService）

现象：`java: 找不到符号 方法 getPageId() 位置 EventCreateDTO`。实际是一整批编译错误。

根因：service 层是按旧数据模型（Page → Event 两级）写的，与实际结构（Book → Event → Page 三级）错位，
DTO / VO / domain 三方字段对不上。`mvn compile` 共暴露出约 110 处 "找不到符号"。

### 三层结构（以 OpenAPI 文档 + schema.sql 为准）
- book ──< event（book_id）──< page（event_id，含 canvas_data）
- book ──< relation_graph（book_id，含 data）
- 前端目录顺序：book → event → page；画布挂在 page 上

### 主要改动
- `EventCreateDTO`：去掉 bookId / sortOrder，只留 name（bookId 走 URL 路径）
- `EventUpdateDTO`：去掉 sortOrder，只留 name
- `PageCreateDTO` / `PageUpdateDTO`：去掉 eventId / sortOrder / canvasData，只留 name
- `RelationGraphCreateDTO` / `RelationGraphUpdateDTO`：去掉 bookId / data，只留 name
- `RelationGraphExtractDTO`：字段改为 `objectTypes` / `relationTypes`（List<String>），去掉 bookId
- 新增 `dto/SortItem`（id + sortOrder），OpenAPI 里批量排序的请求体元素
- `EventService`：createEvent(bookId, dto)、getEventsByBookId、sortEvents(bookId, dto)；页面数走 `countPagesByEventId`
- `PageService`：createPage(eventId, dto)、getPagesByEventId、savePageCanvas（1MB 上限校验）、sortPages
- `RelationGraphService`：createRelationGraph(bookId, dto)、saveRelationGraphData、extractRelationGraph 返回节点/边 JSON
- `RelationGraphDetailVO`：data 原始串之外，新增解析后的 `nodes` / `edges`（List<Map>）
- `BookWorkspaceVO`：按 OpenAPI 重构为 `{book, events[{pages[]}], relationGraphs}`，删掉旧的平铺字段
- Controller 路径全部对齐 OpenAPI：`/api/books/{bookId}/events`、`/api/events/{eventId}/pages`、
  `/api/pages/{id}/canvas`、`/api/books/{bookId}/relation-graphs`、`/api/books/sort`(PUT) 等
- `CanvasController` 不再注册 Bean，画布接口合并进 `PageController`
- `BookService`：注入 Event/Page/RelationGraph 三个 repository，`getBookWorkspace` 组装真实数据，删除案件书时手动级联

## 排查「5173 请求不到后端」+ 修正后端端口

现象：前端 dev server（5173）请求 `/api/*` 拿不到后端。

### 三个叠加的原因（按发现顺序）
1. **`server.port: 0`**——后端随机端口。实测三次分别是 58472 / 58074 / 58074，
   每次重启都变，vite proxy 的固定 target 永远指不到。
2. **8080 被本机 nginx 占用**（`netstat` 确认 PID 是 nginx.exe）。所以即使把后端
   指到 8080 也会冲突；此前 curl 8080 收到的 502 错误页是 **nginx 的**，不是 Spring 的，
   这点很容易误判成「后端崩了」。
3. **WorkBuddy 注入了 `SERVER__PORT=58074`**（注意是**双下划线**）。Spring Boot 的
   relaxed binding 会把 `SERVER__PORT` 归一化成 `server.port`，于是它覆盖了
   application.yml。这也是为什么排查中一度出现「日志显示端口 58074 但配置写的 8081」。
   清环境变量要用 `env -u SERVER__PORT -u SERVER__HOST`，光 `-u SERVER_PORT` 无效。
   此条属于我这边的环境干扰，**不影响用户正常启动**（IDEA 里没有这个变量）。

### 改动
- `application.yml`：`server.port: 0` → `8081`，并加注释说明必须与 vite proxy 一致、
  以及不用 8080 的原因
- `vite.config.ts`：`/api` 与 `/files` 的 proxy target 8080 → 8081
- `utils/coverUrl.ts`：注释里的端口同步
- `api/request.ts`：网络错误文案不再写死 `localhost:8080`（正是它把人带偏了），
  改为按 DEV 环境提示「确认后端已启动且端口与 proxy 一致」
- `WebConfig`：`allowedOriginPatterns("*")` 收紧为 `http://localhost:[*]` /
  `http://127.0.0.1:[*]`，并补 `maxAge(3600)`，注释说明 allowCredentials 与
  allowedOrigins("*") 互斥的坑

### 结论：原 CORS 配置**本身没写错**，只是从没被用上
dev 下走 vite proxy，浏览器眼里是同源（都在 5173），压根不触发 CORS。
`allowedOriginPatterns("*")` + `allowCredentials(true)` 是合法组合（用 allowedOrigins 才会报错）。
改它纯粹是生产环境收紧需要，不是故障原因。

### 验证结果（实测）
- `Tomcat started on port 8081`，直接 curl 接口通过
- CORS 预检：200，`Access-Control-Allow-Origin: http://localhost:5173`、
  `Allow-Credentials: true`、`Allow-Methods`/`Allow-Headers`/`Max-Age` 齐全
- POST `/api/books` → `{"code":200,...,"data":{"id":1,...}}`，业务链路通

### 环境坑备忘（继续记）
- curl 要加 `--noproxy '*'` 并 unset `http_proxy/https_proxy`（本机有 51877 代理），
  否则本地请求会被代理吞掉
- 后台 `&` 起的 java 进程会随 shell 结束被回收，验证要写在同一个 Bash 调用里
  （起服务 → sleep → curl → kill）
